две опции …; сторож «нет пакетов N мс» и надпись поверх последнего кадра; журнал `KastReconnect`».

## Вектор цели

- **Достичь:** пока провал сети короче времени ожидания (по умолчанию 60 с), KAST держит сессию: на экране последний кадр и
  надпись об ожидании, после возврата сети картинка движется дальше, диалога «Код ошибки: -1» нет.
- **Сохранить:** завершение сервером и выход пользователя — сразу (K4).
- **Граница Ф2:** только удержание — один и тот же транспорт переживает тишину. Когда сервер уже отпустил клиента или адрес
  сменился — это Ф3 (авто-возобновление).

## Шаги

- [ ] 1. **Прогон с уликами** — `tools/droprun.ps1 -Seconds N`: чистит logcat, запускает `netdrop.ps1`, переподключает `adb`,
      сохраняет `logcat --pid` KAST и срез журнала сервера за окно провала в `D:\Android\private\evidence\<время>\`, печатает
      итог (строки `KastReconnect`, `Connection terminated`, `Ping Timeout`). Урок Ф1 (находка F1 судьи). Проверка: прогон
      20 с на нынешней сборке — K1 **падает** (контроль инструмента).
- [ ] 2. **Ядро** — в подмодуле `moonlight-common-c`, локальная ветка `kast/enet-timeout`:
      (а) поле `int controlPeerTimeoutMs;` в `STREAM_CONFIGURATION` (`Limelight.h`), 0 = прежние 10000 мс;
      (б) `ControlStream.c:1802` — `enet_peer_timeout(peer, 2, t, t)`, где `t` из поля;
      (в) `LiGetControlStreamSilenceMs()` — сколько мс не было ни одного пакета от сервера по управляющему каналу (ENet
      `peer->lastReceiveTime`; клиент шлёт пинг каждые 100 мс, поэтому в живой сети тишины больше ~100 мс не бывает).
      `FORK: options поле STREAM_CONFIGURATION | глобальный сеттер | константа 60 с · price of error: API ядра, которое
      сливается с апстримом; константа убивает опцию владельца · consulted: соглашение moonlight-common-c — параметры
      соединения живут в STREAM_CONFIGURATION (packetSize, streamingRemotely), LiInitializeStreamConfiguration обнуляет её →
      поле с нулём по умолчанию не меняет поведение у других клиентов`.
      `FORK: options сторож по кадрам декодера | опрос тишины управляющего канала · price of error: ложная надпись на
      неподвижном рабочем столе · consulted: исследование 02, вывод 7 (статус «плохое соединение» считается по кадрам и молчит
      при полной тишине); журнал сервера Ф1 — на неподвижном экране кадры не идут (pop_timeouts), значит сторож по кадрам
      врёт → опрос управляющего канала`.
- [ ] 3. **Мост** — `callbacks.c` (`startConnection`, +параметр), `MoonBridge.startConnection`, `nvstream/StreamConfiguration`
      (+поле и строитель), `NvConnection` передаёт значение. Проверка: сборка; в журнале клиента при подключении —
      `KastReconnect policy grace=60000`.
- [ ] 4. **Опция** — «Время ожидания переподключения» в `PreferenceConfiguration` и `res/xml/preferences.xml`: 10–300 с,
      по умолчанию 60 с. Строки заголовка и пояснения — на всех языках, где есть `strings.xml` (принцип `MASTER_PLAN.md`), с
      проверкой по КЛЮЧУ (EXP-0004). «Интервал повторных попыток» — в Ф3, где он начинает действовать (`[AI]`: мёртвая опция
      в Ф2 путала бы пользователя; K5 закрывается двумя фазами).
      `FORK: options пределы 10–300 с | 10–600 с · price of error: слишком долгое ожидание держит сессию на сервере открытой ·
      consulted: исследование 02 — Citrix 180 с по умолчанию и предупреждение о долгом удержании (A-6.2), GeForce NOW 5 мин
      (A-1.6), Parsec 60 с (A-1.1) → 10–300 с`.
- [ ] 5. **Game** — сторож тишины (раз в 500 мс `LiGetControlStreamSilenceMs`): тишина > 1500 мс → надпись поверх
      последнего кадра «Связь потеряна — жду сеть… N с» (тот же вид, что у надписи «плохое соединение», — вид судит владелец по
      снимку) и строка `KastReconnect silence start`; пакеты пошли → надпись скрыта, `KastReconnect outcome=held elapsed=`;
      `connectionTerminated` во время тишины → `KastReconnect outcome=terminated code=`. Декодер и поверхность не трогаются —
      последний кадр остаётся сам (исследование 02, вывод 6).
- [ ] 6. **Прогоны** — `droprun` 20 с и 5 с, закрытие сервером, контроль с опцией 10 с; отчёт
      `testcases/reports/<дата>_F2_hold.md`; статусы K1, K4, K5, K6, K7 в `testcases/TC_reconnect.md`; снимок надписи — владельцу.
- [ ] 7. **Закрытие** — `/fable-judge`; статусы; план Ф3. Отправка ядра — по ответу на интервью 001.

## Риски

- **Ввод, накопленный за время тишины** (ENet reliable), придёт на сервер пачкой после возврата — вероятно; ответ: на время
  тишины не слать движения мыши/касания (журнал + проверка на прогоне), кнопки — отдельным решением.
- **Сервер отпускает раньше клиента**: `ping_timeout` и `control_peer_timeout` на сервере — 60 с; при времени ожидания
  клиента больше 60 с удержание всё равно кончится на сервере — это работа Ф3; в пояснении опции сказать честно.
- **Правка ядра ждёт ответа владельца** (интервью 001) — Ф2 делается в локальной ветке; указатель подмодуля в KAST не
  отправляется, пока копия ядра не опубликована, иначе чужой клон не соберётся.
- **Канал ~5 Мбит/с до Титана** — установка APK ~70–85 с; прогоны укладывать пачкой.
