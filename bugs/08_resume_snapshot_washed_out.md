**Status:** 🔧 исправлено 2026-09-26 19:40; цвет снимка совпал с живым кадром по замеру (прогон 11); выцветание ушло — слово
владельца; оставшееся «изменение на 10-й секунде» — порядок снимка и освобождения декодера, исправлено 19:47, ждёт взгляда
владельца (прогон 12)
**Version/build:** KAST Debug 20.2.6, сборка 19:15 (`moonlight-noir` @ `c507f57e` + шаг 5) · **When/context:** 2026-09-26 19:28,
тест мерцания на Титане, владелец смотрел на экран
**Severity:** S2 (видимый дефект нового поведения; прогон потерян для оценки перехода)
**Fixing:** эта сессия
**Fix accepted when (observable):**
- Ситуация. Идёт поток «Desktop» на Титане (SDR, ограниченный диапазон), отладочный таймаут ENet 10 с.
- Действие. Сеть хоста пропадает на 25 с.
- Результат. На 10-й секунде картинка на экране не меняется: ни цвет, ни яркость; при возврате снимок плавно переходит в живой
  поток.
- Проверка. Два снимка экрана самим планшетом — на 6-й секунде (живая поверхность) и на 16-й (снимок KAST поверх) — и подгонка
  `node fit_levels.mjs` по всем пикселям: `snapshot = 1.00 × live + 0` в каждом канале; разница пикселей в среднем < 1 уровня.

## Symptom
Слова владельца (дословно, чат 2026-09-26 ≈ 19:28–19:32): «но, какое-то время без сети картинка была сочная, а затем бац -
выцвела, словно HRD пытается на SDR экране отображаться.» · «вот, опять выцвело» · «на 10-й секунде выцветает».

## Forensics
Прогон 10 (`D:\Android\private\evidence\20260926-193131-drop25\color_a.webp`, `color_b.webp` — один и тот же застывший кадр:
живая поверхность и снимок KAST): подгонка по 225 280 пикселям — `snapshot ≈ 1.01 × live + 14`; живые уровни 12 / 77 / 133 →
на снимке 24 / 93 / 143. HDR и полный диапазон в настройках выключены (`checkbox_enable_hdr=false`, `checkbox_full_range=false`).

## Root cause
Декодер получает метки цвета BT.709, ограниченный диапазон, передаточная функция SDR-видео
(`MediaCodecDecoderRenderer.createBaseMediaFormat`). Экран Android показывает SDR-видео как есть, а `PixelCopy` честно переводит
кадр из передаточной функции BT.709 в sRGB битмапа: тёмные тона поднимаются. Расчёт перевода BT.709 → sRGB для 12 / 77 / 133 даёт
26 / 92 / 145 — в пределах 2 уровней от замера.

## Fix
`Game.kastShowLastFrame`: для SDR-потока на API 29+ кадр копируется в битмап цветового пространства BT.709 (без смены
передаточной функции) и затем помечается sRGB без пересчёта (`Bitmap.setColorSpace`) — так, как экран трактует видео. HDR-поток
и API < 29 — прежняя копия sRGB. Прогон 11: `snapshot = 1.0001 × live + 0.00` (R), `1.0002 × live + 0.01` (G),
`0.9997 × live + 0.03` (B); резкость та же (лапласиан 4.054 и 4.053). Владелец: «выцветение ушло, да».

Второй след того же места — «сейчас на 10-й секунде тоже чуть-чуть было изменение картинки» (прогон 11): старый декодер
освобождался сразу, а снимок вставал через 90 мс (`resume start` 19:41:56.846 → `last frame shown` 56.936). Теперь освобождение
ждёт снимка на экране и ещё 50 мс (прогон 12: `resume start` 19:49:23.509 → `last frame shown` .569 → первая попытка назначена
.903).

TWINS: searched `grep -rn "Bitmap.createBitmap\|PixelCopy" app/src/main/java` (2026-09-26 19:52) — кроме `Game.java` 4 места:
`DigitalPad.java:253`, `:260` (картинки экранного геймпада), `CachedAppAssetLoader.java:69` (заглушка 1×1),
`TvChannelHelper.java:124` (картинка канала Android TV); `PixelCopy` нигде больше нет — видео копирует только снимок KAST, класс
один.

Guard: замер двух снимков экрана (живой кадр и снимок KAST) подгонкой уровней — шаг прогона Ф3 в `testcases/TC_reconnect.md`;
модульным тестом цвет поверхности не проверить.

## Decisions made without the owner
- `[AI]` цвет снимка приводится к тому, как экран показывает видео, а не к «правильному» переводу цвета: владелец сравнивает с
  тем, что видел на экране секунду назад.
